# 智能查询直接执行与项目跟进自动研判设计（待评审）

## 目标及已确认需求

用户希望减少智能操作的中间步骤：智能查询理解需求后直接查询并展示结果；智能填写理解需求后直接填入表单。用户已明确选择填写后仍点击原有保存按钮；最初选择跟进中／已联系或领取时自动分析，随后进一步明确：管理员和项目当前负责人共享项目 AI 报告，手写备注仍私有。因此自动跟进 AI 以管理员或项目当前负责人为使用者，普通非负责人仅修改个人状态不触发项目分析。另增加推送原因诊断、模型调度和站内提示，让三个公告入口读取同一份授权项目报告。

本文件是可评审的设计，尚未代表产品功能已经实现。范围是本地开发与验证；不更新 178 服务，不修改生产配置、凭据或原有跟进记录。

## 当前实现与根因

- `assist.js` 登记了今日资讯、推送列表、订阅搜索及旧企业／推荐页面的智能查询。它们现在生成字段草稿，用户再应用、再搜索；查询模型没有读实际查询结果。
- 已有订阅、网站、策略、自动化、模型、账号、跟进备注等填写入口。当前“应用所选建议”可以填表，不需要复制，但仍多一步。
- 当前普通查询的 `q` 是连续文字包含匹配；辅助白名单没有时间范围及未截止条件。`actionable` 表示更严格的参与证据，不能直接等同于“投标截止时间尚未到”。
- `ai.explain`、`assist.generate`、模型连接测试及配置保存共用进程级 `ai.LOCK`，非阻塞获取失败即拒绝。无网络 mock 已复现：占锁时出现相同提示，HTTP 调用次数为零。这是应用限制，不能据此判断服务商不支持并发。
- 已核实当前接入 DeepSeek 官方外部接口；日志另有多次 `truncated response`。当前解读／填写预算为 1600／2200 tokens，未指定外部 DeepSeek thinking 模式。官方文档说明默认开启 thinking；截断原因仍需结合 finish_reason、用量与输出长度核验，不能把推测当成已确认根因。
- 公共解读存入公告 payload；专题解读按用户、专题、公告存储。普通用户从今日资讯直接生成公共解读受限；保存跟进、领取与指派都没有个人自动分析流程。

## 方案取舍

选用现有 SQLite 加后台线程构成持久任务队列，不新增 Redis、Celery 或另一套部署服务。单纯移除锁或使用临时线程池缺少限流、去重及重启恢复；引入独立消息中间件会增加当前部署成本。网络生成不占用数据库写事务，现有 FastAPI、SQLite 与原页面布局继续使用。

查询与填写共用“生成结构化结果—程序校验—执行对应操作”的流程；智能查询通过当前页面真实提交函数执行。此次不建立任意 SQL 执行入口，也不另建全网聊天查询服务。模型负责理解需求，程序负责查询范围、权限和事实条件。

## 一、智能查询理解后直接查询

### 操作方式

1. 输入需求，点击“开始查询”。系统显示理解中／排队中状态。
2. 模型将需求整理成允许的查询字段，服务端校验字段、类型、范围、枚举及可访问专题。
3. 当前页面与请求上下文仍有效时，自动填入查询条件，关闭辅助弹窗，并一次性执行该表单真实提交逻辑；重置到第一页，直接展示结果。
4. 已解析条件以简短条件标签保留，方便后续修改；不要求用户先确认条件或再点搜索。
5. 不支持、相互矛盾或无法确定的条件，明确说明原因，不静默丢弃后执行更宽的查询。没有结果就是零条结果，不能编造项目。

| 入口 | 实际执行范围 |
| --- | --- |
| 今日资讯 | 共享公共库，个人状态叠加在查询结果上 |
| 推送列表 | 当前账号已送达记录，保留当前主题和阅读状态，除非用户明确要求调整 |
| 订阅情况 | 本人订阅的名称、行业和关键词，沿用本地列表筛选 |
| 我的跟进（补齐同类入口） | 本人保存的跟进或本人当前负责的线索 |
| 旧企业／推荐表单 | 表单存在时仍兼容，不恢复已合并的旧导航 |

推送列表的真实渲染由后加载的 `interactions.js` 覆盖，必须修改实际生效的提交链路。统一执行使用 `requestSubmit()` 或提取的真实提交函数，不能仅触发按钮 click，也不能以 `requestSubmit()` 的返回值判断异步查询或保存成功。

### 查询字段补齐

- 扩展有公告数据的查询入口：正文与标题关键词 `terms`、`term_mode=any/all`，发布日期起止、截止状态；保留已有地区、阶段、个人状态、排序与分数条件。关键词是模型整理的具体词与必要同义表达，本轮不宣称已完成向量语义检索。
- `q` 与 `terms` 表达同一个关键词条件，不能作为两个独立条件叠加。智能生成的新关键词替换原 `q/terms`；用户手动改词也替换这一条件，保留其他日期／地区等条件。统一规范化后只传递有效关键词条件，避免旧“燃烧”与新“消防”被意外要求同时满足。
- 日期由后端根据准确北京时间解析。日期起点含当日零时，结束日含全天；数据库过滤使用规范化的半开区间。时间未知的记录不当作符合指定时间范围。
- “未截止”要求明确的投标／响应截止时间尚未到，且未终止、未被后续结果覆盖；截止时间未知另标待核实，不混入明确未截止结果。
- “还能报名／可参与”使用更严格的正文及文件获取状态检查；投标未截止但报名已截止的记录可以按前者出现，但必须标明报名限制。
- 推送查询区分原公告发布日期和站内推送时间。模型只有用户明确表达时才选择推送时间，不能把两者混用。
- 所有过滤发生在分页前；翻页、刷新和普通手动搜索保留智能生成的条件。模型不能擅自修改个人订阅配置。
- 字段支持矩阵固定如下：今日资讯支持公告词、发布日期、截止状态、地区、阶段、分类、个人状态、分数及排序；推送支持公告词、发布日期／推送日期、截止状态、主题、阅读状态及排序；我的跟进支持本人查询词、发布日期、截止状态、个人阶段及排序；订阅搜索仅支持订阅查询词，旧企业入口仅支持企业词和地区，旧推荐入口支持公告词及个人阶段。辅助只生成对应入口可执行的字段；提交、URL／页面状态、翻页、刷新和可用导出共用同一规范化条件。模型要求超出矩阵时明确反馈，不默默丢弃。
- 地区／阶段只接受系统可查询的标准值；复杂需求超出现有字段时返回具体未支持条件。行业分类未覆盖 AI 软件等新业务时，以需求关键词查询，不强制套用垃圾焚烧分类。

准确时钟是时间条件的前置依赖。采用已写的 [北京时间统一时钟设计](2026-10-14-beijing-clock-design.md)，该文件也需评审；仅设置 `+08:00` 或固定加六小时不满足要求。完成授时及相关测试前，不能宣称“近七天／未截止”查询已准确支持。

## 二、智能填写直接填入

- 点击“理解并填写”后，生成结果通过现有字段白名单校验，自动填入，不再展示逐项勾选应用步骤。
- 保留填写前快照；显示本次填入字段的简短摘要和“撤销本次填写”。撤销恢复本次填写前的表单值，不表示回滚已保存的配置。
- 保存、新建、启停、权限、密码、密钥和团队指派仍由原有控件处理。用户已确认本轮不自动保存配置。
- 来源规则被填入后，旧预览令牌失效；保存启用仍需按现有流程测试当前规则。模型不能为未读到的页面捏造选择器或接口。
- 生成跟进计划时直接填入当前备注框，但不会覆盖已保存备注；用户仍通过保存按钮确认。
- 自动应用前，先释放本请求自己的控件锁与 busy 状态，随后重新检查上下文；避免禁用控件被 `assistControls` 排除或自己的 busy 标志阻止应用。

所有入口共同捕获账号、会话代次、页面渲染版本、视图／配置标签、当前实体、请求序号和表单修改版本。切页、关闭弹窗、退出登录、切换账号、打开另一条公告或手动修改表单后，旧结果不得自动覆盖新内容；停止该界面的轮询，并在仍可显示的界面说明结果未应用。一次填写只触发一次必要的联动和一次查询，不因逐字段 change 连续提交。

## 三、模型任务调度和请求适配

### 调度

- 新增 SQLite `ai_jobs`，保存任务类别、操作发起者、结果所属账号、目标公告／专题、输入版本、去重键、优先级、状态、尝试次数、下一尝试时间、领取租约、结果及安全错误码。任务中不保存 API 密钥、已保存私人备注或企业名录联系人。
- 操作发起者、业务上下文所属账号和结果可见范围是独立字段。项目研判任务使用 `visibility=project`、公告 ID 和负责人版本；项目报告及任务结果只能由管理员或该项目当前负责人读取，权限在每次读取时实时核对，不能仅凭历史申请账号授权。普通表单任务仍仅申请账号可读。
- 负责人版本采用每次负责人变更都递增的 `owner_revision`，不以账号相同或秒级更新时间替代；A 转 B 再转 A 仍是新版本。共享项目任务去重键为项目、负责人版本、证据、业务上下文及模型／提示词版本，不含操作发起者，避免管理员和负责人重复生成同一版本。
- 任务类别包括表单／查询理解、手动解读、项目跟进分析、诊断说明、公共自动解读及连接测试。配置保存只保护配置快照，不占用网络生成的全局锁。
- 默认同时最多 2 个模型请求，管理员可设 1–8；按实际服务商响应与部署资源调整，不能按厂商理论上限直接放开。初始后台自动任务同时最多 1 个，前台操作优先；长期等待的后台任务定期提升优先级，已运行请求不强行抢占。
- 通过短事务原子领取任务和校验并发容量。HTTP 调用在事务外执行；完成时再次检查账号、输入版本及任务版本，过期结果不写回当前记录。
- 状态包含等待配置、排队、生成中、等待重试、已完成、已失效及失败。接口立即返回任务标识，页面只在相关界面仍显示时轮询；排队不要求用户重复点击。
- 相同账号、目标及输入版本复用同一个任务或已有结果；连续点击不会重复计费调用。结果缓存使用公告原始证据及业务上下文，排除不断变化的当前时间和采集检查标签。
- 上述排除秒级当前时间仅适用于报告缓存。相对日期查询固定提交时的可信北京时间参考点，并把参考日期、规范化起止边界及查询规则版本纳入去重／缓存键。交互任务从提交起有效 5 分钟；查询结果超时或跨北京时间日期后不得自动应用旧范围，原界面仍有效时以新参考点重建一次任务，仍未完成则显示重试入口。任务状态响应提供可信当前时间用于应用前检查。
- 租约与有效期使用统一时钟；请求总时限用单调时钟。重启恢复过期租约，先核对是否已产生结果；外部调用无法保证费用意义上的 exactly-once，结果发布必须幂等。

### 请求与失败处理

- 抽出统一 provider 请求层，供公告解读、填写、查询和连接测试使用；配置模型、地址和加密密钥不因这次改造被替换。
- 对当前官方 DeepSeek 的短结构化任务显式使用非思考模式；通用兼容服务不注入未经确认的厂商参数。本地模型继续使用原有非思考设置。
- 初始结构化输出预算为 4096 tokens；明确截断时最多再用 8192 tokens 重试一次，同时压缩或按实际需要选择输入证据。记录 finish_reason、可用 token 用量、输出长度及耗时，不记录密钥或原始私人输入到公开日志。
- 网络、429 和可恢复服务端错误最多 3 次尝试，按退避和受限 Retry-After 排队；认证／配置错误等待管理员修正，不能持续请求错误密钥。格式或截断修复也计入总尝试上限。
- 每次请求总时限为 120 秒，响应大小上限为 2 MiB；keep-alive 空行不刷新总时限，数据库连接不在网络期间占用。任务领取租约初始为 180 秒，并在受控执行期间续期；15 秒周期检查过期租约。界面以 2 秒间隔轮询可见任务，离开上下文即停止。
- 模型配置版本变化后，排队任务使用新的有效配置；旧版本响应不能覆盖新版本结果。前台显示可读状态，错误不影响原表单、已保存跟进和规则结果。
- 采集完成后将公共自动解读入队，再独立执行站内推送，不等待 AI 批次。原有每轮最多 5 条公共高分自动解读策略保留；项目跟进自动分析独立于这 5 条。

## 四、管理员和当前负责人共享项目自动研判

### 触发与生命周期

- 员工领取负责人，或当前负责人公开阶段进入“跟进中／已联系”时，登记项目分析任务。管理员指派／转交时，若保留的团队阶段为跟进中／已联系，使用实际接手人的业务上下文登记；归档等非活跃阶段不因转交重新生成。
- 有负责人时，以当前团队阶段为自动资格：负责人账号启用且团队阶段为“跟进中／已联系”。无负责人时，管理员可在自己的个人状态进入这些阶段时触发项目分析；普通非负责人保存个人状态或备注，不触发项目 AI。
- 判断阶段仍复用现有状态，不另造业务阶段。触发、历史补齐、自动更新及自动写回统一检查项目当前负责人／管理员资格和当前授权版本。
- 保存相同阶段或仅修改未送模型的私人备注，不重复分析；重复领取或多位管理员重复操作同版本，不重复提交。
- 公告原始证据、已核实后续状态、负责人、负责人业务上下文、跟进阶段或模型／提示词版本变化时，标记报告需更新并为符合自动资格的项目入队。仅分数重算、最近检查时间变化不触发重复调用。
- “已排除／已归档／待研判”不新增自动分析；历史项目报告保留，读取仍实时核对管理员／当前负责人权限。放弃或转交后，原负责人不再生成或读取项目 AI；其已有个人记录与手写备注保持私有，不删除或移交。
- 小批量补齐扫描按项目去重，为活跃团队跟进及无负责人的活跃管理员跟进补任务。表初始化后运行，不修改状态、不认领、不复制私人数据。
- 普通查看不触发自动分析。管理员或当前负责人可手动生成项目报告，手动生成本身不创建跟进。无负责人时仅管理员可以使用项目跟进 AI。员工自己的订阅／自动化配置智能填写仍可用；这项收紧只针对公告跟进 AI，不扩大到所有表单。

### 输入、结果与存储

- 新增 `project_analyses`，按公告 ID 保存当前项目报告、负责人版本、证据 hash、上下文 hash、模型／提示词版本、生成时间及任务关联；报告不写入所有人可见的公共公告 payload。已有 `topic_analyses` 和私人备注不改为共享，新项目报告由新任务生成。
- 公共事实直接复用已采集的原公告证据：标题、来源链接、发布时间及精度、采购主体、采购范围、金额原文、投标截止／文件获取期限、阶段及后续公告。未知的信息明确写未取得，不能用采集时间补发布时间。
- 有负责人时，业务视角使用该负责人启用且与公告相关的订阅行业、服务能力和关键词；多个主题同时相关时列明采用哪些主题。无负责人时使用触发管理员的业务配置。无相关配置时先生成事实与通用行动报告，并标明能力待补充，不猜测能力。
- 不发送已保存的私人备注、企业联系人或原有私人研判。模型仅使用授权公共证据和上述业务配置；负责人事先知道该项目 AI 报告对管理员共享。
- 报告包含事实摘要、采购需求、业务契合及依据、风险与待核实项、按项目当前阶段的下一步清单。重要事实附原文链接和证据片段；证据必须能在已取得正文中验证，无法验证的断言不作为事实展示。
- 模型不能改公共事实、规则分、跟进阶段、负责人、已完成状态或私人备注。仅列表线索或正文不完整时明确证据限制，不能断言资质满足或建议执行已过期报名／投标。
- 证据 hash 按实际原文和来源发布日期等证据生成，不直接使用包含派生评分的旧 `content_hash`。运行状态 hash 只含截止／后续状态变化，不能含每秒变化的 `current_time`。
- 写回前重新核对当前负责人／管理员权限、任务版本、负责人版本、公告证据、业务上下文及手动／自动资格；转交期间的旧负责人任务失效，使用新负责人上下文的新任务才可发布。管理员发起者不会被错误地当成被指派人的业务身份。

### 展示与权限

- 管理员和当前负责人从今日资讯、推送列表、我的跟进及团队跟进打开同一公告，展示同一份“项目 AI 研判”；授权列表显示排队、生成中、已生成、需更新或失败。其他用户可看公共公告与公开负责人，但不显示项目 AI 正文或公告跟进 AI 填写入口。
- 已有公共和专题解读仍明确区分；项目报告作为授权跟进详情的主要 AI 区域，避免把相同分析重复展开。跟进计划智能填写也在后端收紧为管理员或当前负责人，不能仅隐藏按钮；草稿填入操作者自己的备注框，仍由本人保存，不写对方备注。
- 报告失败可重试；有旧报告时标明旧版本，不用失败清空已生成内容。
- 项目报告与任务结果在提交、执行、写回、轮询、详情及历史读取时均核对实时权限。转交／放弃后，旧负责人失去项目 AI 权限，界面清除其失效项目报告区域。原有私人专题解读和手写备注仍只归本人，不随负责人转交。

## 五、转交同步与站内提示

- 当前代码转交后已更新团队负责人和保留的阶段。接手人下次进入／刷新“我的跟进”即可看到该项目，不需要先创建个人记录；已打开页面尚无主动同步。转交不会凭空新增订阅推送。
- 新增独立站内通知，不混入订阅推送列表。转交事务同时登记接手人通知及原负责人的转交通知，管理员操作成功提示明确写“已转交给某人，已进入其我的跟进”。重复指派同一人不重复通知。
- 无负责人时管理员可以直接选择员工并“指派”，不需要先领取为自己负责人再转交；已有负责人时使用“转交”。员工主动领取后，管理员重开详情的团队跟进区域显示“已跟进 · 负责人：姓名”和公开阶段，管理员个人研判状态保持独立。
- 当前员工领取项目、负责人公开跟进阶段变化及有效项目报告完成／最终失败时，在对应业务事务提交成功后给启用管理员登记按事件版本去重的站内通知。失效任务不发布完成／失败通知，非负责人私人状态或备注变化不发团队事件，不在通知中复制备注内容。
- 员工侧栏“我的跟进”右侧显示红色圆圈数字，数字为本人当前负责且尚未查看的管理员派发项目数；零条隐藏，超过 99 显示 `99+`。打开列表、翻页和筛选不清红圈；成功打开一个具体项目详情后，只标记该指派版本已查看。桌面和移动端都显示红圈及可访问的未读数字说明。
- 派发记录在“我的跟进”显示“管理员派发”，已查看后来源标记仍保留；未查看时加“新指派”。员工主动领取不增加派发红圈；转交／放弃后旧指派不再计入当前红圈。历史来源无法核实时不补造管理员派发标签。
- 通知入口可打开项目；管理员团队看板显示待处理通知及 AI 任务状态。项目详情打开时再次核对当前负责人及报告权限。指派查看确认带确切 `owner_revision`，延迟到达的旧确认不能消掉新的指派红圈；其他账号和管理员团队统计不能读取员工指派查看状态。
- 登录后和页面可见时最多每 15 秒检查本人通知／负责人变更，切换账号后立即清空上一账号通知状态。只刷新当前合法的数据区域，不打断编辑草稿；数据在事务提交后可读，前台自动同步以这个轮询窗口为界。
- 新增通知只包含事件类型、公开项目标识／标题、公开负责人和阶段及安全任务状态；管理员接收范围为启用管理员，接手人接收自身指派。原负责人通知只说明已转交，不带新报告或新负责人的业务分析。
- 通知是否已读由本人操作维护，阅读通知不改变订阅推送的阅读记录、跟进状态或负责人。历史转交不补发海量新通知；通知从此功能启用后的事件开始。

## 六、推送原因诊断

- 在订阅情况的主题详情及推送列表无结果处提供“查看推送诊断”。先执行程序统计并立即显示，再按用户主动请求入队生成简短解释。
- `GET /api/subscriptions/{id}/diagnosis` 只返回已授权的结构化统计；本人可看本人主题，管理员可看团队订阅的授权统计。诊断解释任务使用相同数据，不读取私人备注、阅读状态或其他用户的推送正文。
- 检查账号、订阅、个人推送计划、全局调度、待首次检查／待修订检查、上次成功检查和当前可用来源。
- 使用与实际订阅匹配相同的公共库范围、文字包含及来源观察逻辑，按来源—地区—阶段—关键词—标题排除的顺序给筛选漏斗。另展示去掉单项限制后的数量，说明统计先后次序，不能把先被筛掉的记录全归因于另一项条件。
- 展示当前匹配数、尚未送达数、已由其他主题送达数，以及当前待补充本主题关联数。后者指当前已匹配且已有站内推送、但该推送尚未关联本主题的记录数；本轮不追溯上次执行实际新增关联数，现有历史没有关联时间证据。同账号同公告只推送一次，`last_count=0` 不等于没有匹配。
- 只使用公开安全的来源可用性、采集统计和实际公共样本。当前库无匹配不能证明网站没有此业务或没有需求。
- 模型解释统计并建议可验证的调整预览；不自动放宽筛选、不启用任务、不修改订阅或执行采集。

## 七、接口与兼容

- 新任务接口围绕原 `AssistRequest` 和各任务类型做白名单校验；普通填写／查询任务仅本人可读，项目任务仅管理员或实时当前负责人可读。重试接口重新校验权限、最新证据、负责人和上下文。
- 新增项目分析读取／重新生成和本人站内通知接口；公告详情和各跟进列表仅为授权人附加项目报告状态。普通负责人不需要专题才能生成项目研判，公共 AI 写权限仍限管理员。
- 原同步辅助和分析接口保留兼容返回路径，通过统一调度层等待有限时间；新前端采用任务标识轮询。旧客户端的等待超时返回明确错误及已创建任务标识，不把忙碌伪装成模型失败。
- 全部新过滤参数有类型、长度、数量与枚举限制；普通搜索、导出、分页及推荐／推送所用条件保持一致，SQL 由程序构造并绑定参数。
- 样式沿用现有弹窗、表单和详情卡片。密码、API Key 和权限控件不会成为智能填写字段。

## 八、验收条件

1. 各智能查询一次操作后显示实际搜索结果；不用应用条件再点搜索。近七天、未截止、正文关键词、多词关系在后端按正确时间和分页顺序验证；未知截止、报名已截止、已终止及后续结果有明确测试。
2. 各填写入口生成后自动填入、一次撤销恢复原值、仍未保存；源规则令牌失效，账号密码及权限不被填写。followup 控件锁不阻挡自身应用。
3. 延迟响应期间切页、换账号、关闭弹窗、打开另一公告或手改字段，旧结果不会误填；查询不会逐字段触发多次。
4. Mock 并发与调度验证默认 2、后台 1、前台优先及公平性；忙碌任务入队，重复操作去重，重启恢复、租约、配置变化和旧结果拒绝成立。
5. 使用 MockTransport 验证 thinking 参数兼容、JSON 校验、截断、预算重试上限、429／5xx／网络退避及认证暂停；不以线上模型波动作为单元测试通过标准。
6. 双用户及管理员测试项目报告共享边界、非负责人拒绝、转交撤销旧负责人报告与任务结果权限、指派使用接手人上下文、项目历史补齐、放弃后私人记录保留、内容／阶段变化重生成和各入口一致；旧私人解读不转为共享，私人备注不进入模型 payload。
7. 诊断统计与真实匹配一致，覆盖零匹配、暂停、待首次检查、跨主题已送达、正文命中及来源部分可用；诊断不改变订阅或任务。
8. 运行相关测试及完整测试集，浏览器验证直接查询、自动填入／撤销和个人任务状态；保存截图供用户查看。真实模型核验只使用明确选择的少量公开样本或无私人数据测试，不批量发送全部历史跟进。
9. 本地替换前备份配置与 SQLite 一致性快照；迁移只新增所需表／字段，保留业务数据、原有权限、首次推送依据和负责人规则。服务器发布单独安排。
10. 通知测试包含领取、指派、转交、重复指派、报告完成／失败、公开阶段变化、私人备注不通知、通知已读归本人及切账号清理。转交不新增订阅推送，接手人自动同步我的跟进；打开列表不清红圈，详情成功仅清对应版本，A→B→A 的旧确认不清新指派；来源标记已读后保留。员工主动领取后管理员详情显示已跟进及姓名，编辑中的草稿不被轮询覆盖。
